# AIOps triage-бот (веха M1: только советник)

Alertmanager отдаёт этому сервису один сработавший алерт. Бот собирает
read-only доказательства из Prometheus и Loki, решает, что делать - или
отказывается решать - и кладёт результат в Telegram карточкой с кнопками
**согласиться / подробнее / отчёт / игнор**. В M1 он не выполняет ничего, и это свойство
артефакта, а не обещание в документе (см. [Guardrail](#guardrail)).

Образ - `python:3.12-slim` плюс один пакет: **ни зависимостей, ни
Kubernetes-клиента, ни `kubectl`, ни shell**. Весь список зависимостей - это
стандартная библиотека, поэтому `unittest` целиком закрывает тестирование, а CI
не нужны ни `pip install`, ни lock-файл, ни кэш.

## Что происходит с одним алертом

    Alertmanager --POST /alert--> server.py
                                   |
                                   +- filter    aiops="true", status=firing, не snooze,
                                   |             не дубликат (окно 30 минут)
                                   +- context   Prometheus (запланированные запросы) +
                                   |            Loki (логи); всё несобранное -> `missing`
                                   +- tier 0    MockAdapter - таблица правил прямо в коде
                                   |            уверенный ответ? -> готово, модель не зовём
                                   +- tier 1    модель, ТОЛЬКО если tier 0 эскалировал
                                   |            (DeepSeek / OpenAI / Ollama / любой
                                   |             OpenAI-совместимый шлюз)
                                   +- validate  строгий JSON, action_id из whitelist,
                                   |            параметры в диапазоне, confidence >= порога
                                   +- notify    карточка в Telegram + журнал + /metrics
                                                ничего не исполняется

Три свойства этой картинки стоит проговорить явно: каждое из них - ответ на
поломку, которая в проекте уже случалась один раз.

* **модель не нужна, чтобы бот был полезен** - tier 0 это таблица правил, и её
  одной достаточно: она отвечает на алерты, которые этот стенд реально стреляет,
  из таблицы, которую тест держит синхронной с файлом правил. `MODEL_ADAPTER`
  выбирает tier 1 (в отгружаемом ConfigMap - `deepseek`); значение `mock` там
  значит «модели нет вообще» - офлайн-стенд и CI;
* **модели никогда не доверяют** - её ответ идёт через тот же валидатор, что и
  ответ таблицы правил, а отвергнутый ответ становится эскалацией, но не
  действием;
* **пропуск сообщается, а не заполняется** - то, чего бот не увидел (события
  подов, условия нод, вывод `describe`), перечислено в `missing` на карточке.
  Честный пропуск стоит одну строчку; догадка стоит доверия ко всем остальным
  строчкам.

## Guardrail

M1 - советник: он может предложить, но не может выполнить. Это держится на
четырёх независимых уровнях, поэтому ошибки в любом одном из них недостаточно,
чтобы граница сломалась:

| Уровень | Факт | Где видно |
| ------- | ---- | --------- |
| Pod | `automountServiceAccountToken: false` и нет `serviceAccountName` - значит, нет и токена, которым можно аутентифицироваться | `manifests-aiops/02-triage-bot-dep.yaml` |
| RBAC | ни Role, ни ClusterRole, ни RoleBinding, ни ClusterRoleBinding во всём компоненте | grep в CI-джобе `aiops-tests` и проверки в `tests/test_manifests.py` |
| Образ | нет `kubectl`, нет shell, нет Kubernetes-клиента, который можно импортировать | `Dockerfile`; в CI - `docker run --entrypoint python ... -c "import triage_bot, ..."` |
| Код | whitelist действий и схема решения живут в `triage_bot/model.py`, а `TriagePipeline.execute()` бросает `NotImplementedError` | `model.ACTIONS`, `pipeline.execute()` |

Whitelist лежит в коде намеренно. В ConfigMap его мог бы править любой, у кого
есть право править конфигурацию, и «модель не может сделать ничего
неодобренного» превратилось бы в «модель не может сделать ничего вне списка,
который кто-то выбрал на прошлой неделе». `pipeline.execute()` существует ровно
чтобы сказать это вслух, а его docstring - это спецификация того, что должна
добавить веха M2.

## Контракт решения

Оба уровня отвечают одной и той же формой - один JSON-объект и ничего больше:

```json
{"action_id": "restart_deployment",
 "confidence": 0.85,
 "reason": "1-3 предложения по-русски",
 "evidence": ["replicas_available[front-end] = 0", "log: connection refused"],
 "params": {"namespace": "sock-shop", "deployment": "front-end"}}
```

| Ключ | Обязателен | Правило |
| ---- | ---------- | ------- |
| `action_id` | да | одно из четырёх id ниже - whitelist и есть `model.ACTIONS` |
| `confidence` | да | число в `0..1`; ниже `CONFIDENCE_THRESHOLD` (0.7) действие отвергается, а инцидент эскалируется |
| `reason` | да | непустой текст, обрезается на 600 символах |
| `evidence` | да | непустой список; его элементы берутся из собранного контекста, а не из воображения модели (не больше `MAX_EVIDENCE_ITEMS`) |
| `params` | для действий, которым нужны | ровно ожидаемый набор: `namespace` и `deployment` - имена по DNS-1123, `replicas` - целое в `1..10`, а `namespace` обязан входить в `ALLOWED_NAMESPACES` |
| `proposal` | нет | свободный текст, максимум 500 символов, **разрешён только вместе с `escalate_human`** |

| `action_id` | Риск | Команда, которую выполнил бы M2 |
| ----------- | ---- | ------------------------------- |
| `restart_deployment` | низкий | `kubectl -n {namespace} rollout restart deployment/{deployment}` |
| `rollback_deployment` | средний | `kubectl -n {namespace} rollout undo deployment/{deployment}` |
| `scale_deployment` | средний | `kubectl -n {namespace} scale deployment/{deployment} --replicas={replicas}` |
| `escalate_human` | нет | (команды нет - инцидент уходит человеку) |

Каждую команду рендерит **этот код** из провалидированных параметров. Текст модели
никуда не подставляется, а `_NAME_RE` отбрасывает имя раньше, чем оно могло бы
дойти до shell. Лишние ключи, ответ прозой, markdown-забор, неизвестное действие,
`replicas: 0` - всё это отказ, а отказ - это **эскалация с причиной**, посчитанная
в `aiops_schema_violations{kind=...}`. Промпт, который выдаёт невалидные ответы, -
это дефект, который надо измерить, а не загадка, которую надо перезапросить.

`proposal` - единственное место, где разрешён свободный текст, и только рядом с
`escalate_human`: это то, что модель сделала бы, будь whitelist шире. Его
показывают человеку, и нигде нет кода, который превратил бы его в команду.

## Каскад: tier 0 - это не заглушка

`MockAdapter` - это и есть таблица правил уровня 0: решения, написанные руками и
привязанные к именам алертов, которые стреляет этот стенд
(`manifests-monitoring/05-prometheus-alertrules.yaml`). Это не подмена модели, а
первый ответ - и на стенде, который ведёт себя прилично, обычно единственный:

* **ключи не могут разойтись с правилами** - `tests/test_coverage.py` валит CI,
  если у отгруженного правила с меткой `aiops="true"` нет ответа в таблице, так
  что «бот забыл про новый алерт» ловится до демо;
* **карточка не выдумана** - *решение* шаблонное, а вот *доказательства* и
  *параметры* приходят из живого контекста: реальные значения Prometheus, реальные
  строки Loki, реальные метки алерта;
* **таблица детерминирована**, и именно поэтому `EVAL_MODE` осмыслен: это база, с
  которой сравнивается ответ модели на том же самом алерте;
* **`ProbeFailed` и `ProbeSlow` намеренно ниже порога уверенности**, поэтому на
  них открывается уровень модели - и тест проверяет ровно это.

`EVAL_MODE=1` зовёт модель даже тогда, когда таблица ответила, сохраняет оба
ответа в журнале и на карточке, но решающим остаётся ответ таблицы. Так
«модель стоит своих денег» превращается в числа (`aiops_incidents_tier{tier=...}`,
токены, задержка, совпадение), а не в мнение.

## Что нашли живые прогоны

Всё это нашлось запуском бота против живого стенда - не чтением кода, потому что
тесты были зелёными и до, и после.

**1. Селектор Loki просил метку, которой не существует.** Promtail вырезает свои
метки из *пути к файлу логов* на ноде
(`manifests-logging/04-promtail-configmap.yaml`), поэтому Loki знает `namespace`,
`pod_name` и `container_name` - а меток `pod` и `deployment` у него нет вообще.
Первая версия переиспользовала прометеевские имена, селектор не совпал ни с чем,
и карточка сказала «loki: no log lines in the window» про front-end, который в
этот момент непрерывно писал логи. Исправлено в `context.collect_context`; тест
(`tests/test_context.py`) падает, если селектор когда-нибудь вернётся к `pod=`.
Проверено на живом стенде: `GET /loki/api/v1/labels` отвечает ровно
`container_name, filename, job, namespace, pod_name, stream`.

**2. Tier 0 доверял алерту.** Синтетический POST `DeploymentReplicasUnavailable`
про абсолютно здоровый front-end выдал уверенный `restart_deployment`. Алерт был
единственным входом, который таблица проверяла. Теперь каждый ответ таблицы, чей
алерт перечислен в `MockAdapter.PREMISES`, перепроверяется по той самой серии, из
которой он должен вычисляться (`replicas_available` против `replicas_desired`), и
противоречие превращает ответ в эскалацию, несущую **оба числа**:

    Алерт DeploymentReplicasUnavailable не подтверждается метриками
    (replicas_available=1 >= replicas_desired=1): состояние уже соответствует
    желаемому, автоматический шаг ничего не исправит - решение за человеком.

Асимметрия здесь намеренная и составляет всю политику: бота останавливает только
**противоречие**. **Отсутствующая** метрика - не конфликт: молчание не должно
блокировать безопасный шаг, иначе бот перестанет действовать на любом стенде, где
сломан один экспортёр.

**3. Поле в health, которое врало.** `/healthz` показывал
`model_tier_reason: "the provider has no base_url"` на стенде с `MODEL_ADAPTER=mock`,
где не отсутствует вообще ничего. Теперь `model_tier_reason` возвращает пустую
строку для `mock`, потому что `mock` *и есть* таблица уровня 0: вводящее в
заблуждение поле в health стоит дороже трёх строк, которые его убирают.

**4. «No log lines» про деплоймент, у которого нет подов.** В демо M1 `front-end`
был отмасштабирован в `0`, и карточка перечислила
`loki: no log lines in the window` - ровно ту фразу, которую давал сломанный
селектор из поломки 1, поэтому она указывала читателю на Loki, а не на
`desired=0`. В контексте уже лежало `replicas_desired[front-end]=0`;
`context._is_scaled_to_zero()` теперь его читает, и карточка говорит
`loki: no pods - the deployment is scaled to 0 (desired=0), so there is nothing to
log`. Неизвестное число оставляет прежнюю формулировку: из молчания тоже нельзя
делать диагноз.

### Живой прогон модели: первый настоящий `bad_params`

`run-local.ps1 -Model deepseek -Alertname ProbeFailed -Fresh` против стенда:
уровень 0 эскалировал по собственной уверенности (0,60 против порога 0,70 — так
задумано, а не сбой), `deepseek-chat` ответил за **1,6–1,9 с** и **~900 токенов**, и
его ответом был `escalate_human` **с** приложенными `deployment`, `namespace` и
`replicas`. У `escalate_human` параметров нет, поэтому валидатор выбросил ответ,
оставил эскалацию и записал причину:

```
answer rejected by the validator (bad_params):
escalate_human needs exactly no params, got ['deployment', 'namespace', 'replicas']
```

Действие верное, форма — нет: ровно тот случай, ради которого существует проверка
схемы. Ревьюер, читающий только `action_id`, одобрил бы решение, которое контракт
уже отклонил. Два прогона — один и тот же исход.

## Локальный запуск (без пересборки кластера, без ключа, без Docker)

```powershell
cd aiops\triage-bot
.\run-local.ps1                  # только tier 0: model=mock, Telegram выключен
.\run-local.ps1 -Fresh           # сначала очистить локальный журнал
.\run-local.ps1 -Model deepseek  # тот же каскад, что в кластере, но с ключом
```

Скрипт достаёт Loki через `kubectl port-forward` (Prometheus уже опубликован на
хост-порту 9090 маппингом k3d), поднимает `python -m triage_bot` на порту
**8090**, отправляет реалистичный payload Alertmanager и печатает три вещи: ответ,
последний инцидент в том виде, в каком его видит человек, и метрики `aiops_*`.

| Параметр | По умолчанию | Почему именно так |
| -------- | ------------ | ----------------- |
| `-Model` | `mock` | `mock`, `deepseek`, `openai`, `ollama` - каскад идентичный, меняется только адаптер tier 1 |
| `-Alertname` | `DeploymentReplicasUnavailable` | любой алерт, который знает таблица правил; подставьте выдуманный и увидите эскалацию |
| `-Port` | `8090` | **не** 8080: этот хост-порт занят Ingress'ом фронтенда (Traefik), а Windows спокойно даёт забиндить уже занятый порт - тогда POST уходит в Node и отвечает `Cannot POST /alert` |
| `-Fresh` | выключен | без него второй POST внутри 30-минутного окна дедупа (правильно) помечается как `duplicate`. Запустите один раз с `-Fresh`, а второй без: это работает фильтр дубликатов, а не сломанный бот |

`-Model deepseek` читает `DEEPSEEK_API_KEY` из `deploy\secrets.local.ps1` (файл в
.gitignore, тот же, из которого собирается Secret для алертинга), копирует его во
временный файл - потому что код читает секреты из **файлов** (`LLM_API_KEY_FILE`) и
никогда из переменной - и удаляет этот файл в блоке `finally`. Ключ не печатается,
не передаётся в командной строке и не попадает в журнал.

## Развёртывание

```powershell
.\deploy.ps1 -WithAIOps              # сборка + импорт + Secret + apply + ожидание
.\deploy.ps1 -WithAIOps -SkipBuild   # только повторный apply
```

`-WithAIOps` делает пять вещей, именно в этом порядке:

1. `docker build -t triage-bot:0.1.0-m1 aiops/triage-bot` - этот тег назван в
   `02-triage-bot-dep.yaml`, и тест утверждает, что они не могут разойтись;
2. `k3d image import triage-bot:0.1.0-m1 -c <cluster>` - образ нигде не
   опубликован, и именно поэтому в Deployment стоит
   `imagePullPolicy: IfNotPresent`;
3. идемпотентно создаёт Secret `aiops-llm`, если есть `DEEPSEEK_API_KEY` (или
   `deploy\secrets.local.ps1`), и иначе просто печатает, что пропускает шаг -
   монтирование `optional: true`, поэтому стенд без ключа всё равно работает;
4. `kubectl apply -f deploy\kubernetes\manifests-aiops` (никогда `examples\`:
   `kubectl apply -f <dir>` не рекурсивный);
5. ждёт окончания rollout и печатает по одной итоговой строке на каждый шаг.

Сменить провайдера tier 1 - это правка ConfigMap, а не кода: поставьте
`MODEL_ADAPTER` в `01-triage-bot-configmap.yaml` и примените заново. В
отгружаемом значении стоит `deepseek`, поэтому на любом алерте, где таблица
правил не уверена, следующая карточка несёт оба ответа - и таблицы, и модели;
`openai` и `ollama` - строки той же таблицы провайдеров. `MODEL_ADAPTER: mock`
означает, что уровня модели нет вообще и конвейер заканчивается на таблице
правил: это офлайн-стенд (без ключа и без выхода в сеть) и именно на нём идут
модульные тесты.

## Справочник по конфигурации

Всё - переменные окружения, которые подаёт `01-triage-bot-configmap.yaml`; файла
конфигурации, который надо парсить, нет, и именно поэтому образу не нужна YAML-
библиотека. Секреты - единственное, что *не* переменная: `llm_api_key()` и
`telegram_token()` читают смонтированные файлы, потому что переменная окружения
видна в `kubectl describe pod` и любому дочернему процессу.

| Переменная | По умолчанию в коде | Ставит ConfigMap | Смысл |
| ---------- | ------------------- | ---------------- | ----- |
| `LISTEN_HOST` / `LISTEN_PORT` | `0.0.0.0` / `8080` | - | где слушает `ThreadingHTTPServer` |
| `MODEL_ADAPTER` | `mock` | `deepseek` | `mock`, `deepseek`, `openai`, `ollama`; неизвестное имя показывается, но не угадывается |
| `MODEL_NAME` | по провайдеру | - | переопределяет id модели (`deepseek-chat`, `gpt-4o-mini`, `llama3.1`) |
| `LLM_BASE_URL` | по провайдеру | - | любой OpenAI-совместимый шлюз, включая vLLM и LiteLLM-прокси |
| `LLM_API_KEY_FILE` | по провайдеру | - | смонтированный файл ключа; пустой файл = без ключа (Ollama) |
| `LLM_TEMPERATURE` | `0.0` | - | ноль: инцидент - это факт, а не творческая задача |
| `LLM_MAX_TOKENS` | `700` | `700` | хватает на одно JSON-решение и достаточно мало, чтобы быть дешёвым |
| `LLM_TIMEOUT_SECONDS` | `30` | `30` | медленный провайдер не должен держать вебхук открытым вечно |
| `CASCADE_ENABLED` | `1` | `1` | звать модель только когда таблица правил сама эскалирует |
| `EVAL_MODE` | `0` | `0` | звать модель даже при ответе таблицы и хранить оба ответа |
| `LLM_FALLBACK_TO_MOCK` | `1` | - | нет ключа: откат на таблицу и **явное сообщение** об этом в карточке |
| `CONFIDENCE_THRESHOLD` | `0.7` | `0.7` | ниже этого действие отвергается и превращается в эскалацию |
| `REQUIRE_LABEL` | `aiops` | `aiops` | разбираются только алерты с этой меткой |
| `ALLOWED_NAMESPACES` | `sock-shop` | `sock-shop` | единственные namespace'ы, которые бот может *называть* |
| `DEDUPE_WINDOW_SECONDS` | `1800` | `1800` | один fingerprint внутри окна - один инцидент |
| `LOG_WINDOW_SECONDS` | `900` | `900` | насколько назад Loki спрашивается о строках |
| `MAX_LOG_LINES` | `40` | `40` | строк логов на инцидент - карточка, а не дамп логов |
| `MAX_EVIDENCE_ITEMS` | `6` | - | более длинные доказательства обрезаются |
| `HTTP_TIMEOUT_SECONDS` | `10` | `30` | 30 под первый запрос к холодной TSDB (см. комментарий в ConfigMap) |
| `PROMETHEUS_URL`, `LOKI_URL`, `ALERTMANAGER_URL` | имена в кластере | те же | read-only источники |
| `TELEGRAM_TOKEN_FILE` | `/etc/aiops/secrets/...` | `/etc/aiops/telegram/telegram_bot_token` | токен - это файл, а не переменная |
| `TELEGRAM_CHAT_ID` | (пусто) | чат стенда | не секрет: он и так виден в ConfigMap Alertmanager |
| `TELEGRAM_MAX_PER_HOUR` | `20` | `20` | дальше - `aiops_telegram_suppressed`, при этом бот продолжает разбирать алерты |
| `JOURNAL_DIR` | `/data` | `/data` | единственный writable путь (корень read-only) |
| `LOG_LEVEL` | `INFO` | `INFO` | |

`tests/test_manifests.py` вычитывает ключи ConfigMap из YAML и имена переменных из
`config.py::from_env` и падает, если имя есть в одном и нет в другом. Опечатка в
ключе ConfigMap иначе невидима: бот молча оставляет значение по умолчанию, и никто
не замечает этого до демо.

## HTTP-поверхность

| Маршрут | Что отвечает |
| ------- | ------------ |
| `POST /alert` | Вебхук Alertmanager: `{"received": N, "triaged": [...], "skipped": [...]}`. Плохое тело - это `400` (Alertmanager повторит, и это будет громко); сбой *разбора* - это `200` с ошибкой в теле, потому что упавшая модель не должна превращаться в шторм повторов по боту |
| `GET /healthz` | `{"status": "ok", "version": ..., "settings": {...}}` - вся конфигурация без секретов, поэтому «какой адаптер ответил» не требует карточки |
| `GET /metrics` | текстовый формат Prometheus |
| `GET /incidents?limit=N` | журнал, новые сверху (по умолчанию 10, максимум 200) - те же данные, которые человек видит в чате; именно это делает стенд отлаживаемым без Telegram |
| `POST /decision` | Синтетическое нажатие кнопки (`{"incident_id": ..., "action": "approve"}`); вызывает *тот же* метод конвейера, что и callback Telegram, поэтому оффлайн-демо не может разойтись с настоящим |

## Карточка в Telegram

Один инцидент - одно сообщение: сначала причина, потом факты, на которых она
держится, и только затем шаг - команда из whitelist, свободный текст, который бот
отказывается исполнять, или runbook самого алерта, если команды нет. Служебные
поля (адаптер, токены) - одна строка внизу; сравнение уровней остаётся в журнале,
где оно является измерением, а не новостью.

Кнопки берутся из whitelist, а не из текста. `approve` существует только для
исполнимого решения - у эскалации есть follow-up'ы и `ignore`. `💡 подробнее`
делает **второй вызов модели, в прозе** (без JSON-схемы, без валидатора, без
исполнения): несколько гипотез, чем их подтвердить и что их отбросит. `📄 отчёт`
отправляет инцидент Markdown-документом (`triage_bot/report.py`), в котором есть
и каскад, скрытый из карточки, и все нажатия людей с временем - артефакт, который
переживает чат. Оба read-only: отчёт собирается из журнала, поэтому нажатие не
ходит в кластер. Повторное «подробнее» в течение 30 секунд отклоняется, а не
оплачивается дважды.

`ignore` усыпляет fingerprint на **4 часа** (`SNOOZE_SECONDS`), и следующее
срабатывание этого fingerprint пропускается как `snoozed`; каждое нажатие
пишется в журнал и считается в `aiops_decisions_recorded{decision=...}`. В M1
ни одно из них ничего не исполняет, и чат отвечает ровно тем, что было записано.

Команды в чате: `/status` (конфигурация и лимиты), `/last` (последний инцидент),
`/help`; всё остальное игнорируется намеренно.

## Метрики

`/metrics` - это реестр текстового формата на 60 строк, а не зависимость, а Service
несёт `prometheus.io/scrape: "true"`, поэтому его подбирает существующая джоба
`kubernetes-service-endpoints`. Именно это делает возможным алерт на *самого бота*:
triage-бот, который молча перестал работать, хуже, чем его отсутствие.

| Серия | Смысл |
| ----- | ----- |
| `aiops_alerts_received{status}` | что доставил Alertmanager |
| `aiops_alerts_skipped{reason}` | `resolved`, `not_labelled`, `snoozed` |
| `aiops_alerts_deduped` | отброшено внутри 30-минутного окна |
| `aiops_incidents{action_id}` / `aiops_escalations{reason}` | что решено |
| `aiops_incidents_tier{tier}` | `rules` или `model` - каскад, измеренный в числах |
| `aiops_model_calls{adapter}` / `aiops_model_errors{adapter}` | цена и отказы по адаптерам |
| `aiops_schema_violations{kind}` | модель ответила, но не по контракту |
| `aiops_context_failures{source}` | Prometheus или Loki замолчали |
| `aiops_telegram_sent` / `aiops_telegram_suppressed` | доставлено или подавлено лимитом |
| `aiops_telegram_documents` | отчёты, доставленные файлами |
| `aiops_decisions_recorded{decision}` | нажатия кнопок людьми |
| `aiops_build_info{version,tier1}` | всегда `1` - сэмпл, доказывающий, что пустой `/metrics` жив |
| `aiops_last_incident_timestamp_seconds` | свежесть - gauge, по которому читается алерт «бот замолчал» |

## Тесты и CI

```powershell
cd aiops\triage-bot
python -m unittest discover -s tests -t . -v      # 136 тестов, секунды, без сети
```

| Файл тестов | Что он фиксирует |
| ----------- | ---------------- |
| `test_model.py` | схему решения: неизвестное действие, отсутствующий ключ, `replicas: 0`, проза вместо JSON, `proposal` без `escalate_human` |
| `test_adapters.py` | таблицу правил, `PREMISES` (противоречие эскалирует, отсутствующая метрика - нет), таблицу провайдеров, прозаический путь `answer()` |
| `test_context.py` | PromQL-запросы, **имена меток Loki** (тот самый баг), `missing` при любом сбое, формулировку при `desired=0` |
| `test_pipeline.py` | порядок каскада, дедуп, snooze, метрики уровней, причины эскалаций, две кнопки-follow-up |
| `test_report.py` | отчёт: причина -> основания -> шаг, скрытый из карточки каскад, нажатия в хронологии, таблицы, переживающие `\|` |
| `test_telegram.py` | карточку, четыре кнопки для действия и три для эскалации, собранный вручную multipart `sendDocument` |
| `test_server.py` | пять маршрутов, `400` на плохое тело, `200` на неудачный разбор |
| `test_coverage.py` | у каждого отгруженного правила с `aiops="true"` есть ответ в таблице - и наоборот |
| `test_manifests.py` | 15 проверок между YAML и кодом: ключи ConfigMap против `config.py`, тег образа против `deploy.ps1`, guardrails, URL вебхука в Alertmanager |

CI гоняет этот набор в джобе `aiops-tests`, затем грепает guardrails M1 из YAML
*вторым, независимым* способом (`automountServiceAccountToken: false`, нет
`serviceAccountName`, нет ни одного RBAC-вида, `readOnlyRootFilesystem: true`), и
напоследок собирает образ и делает import-smoke. Поэтому красная джоба всегда
означает, что ошибка в нашем коде, а не то, что провайдер недоступен или кончился
ключ. Манифесты дополнительно валидируются `kubeconform -strict`.

## Ограничения M1 (намеренные)

* **Он ничего не исполняет.** `dry_run` равен `True` по построению, а `execute()` -
  это `NotImplementedError`, в docstring которого лежит спецификация M2.
* **И доступа на чтение к Kubernetes тоже нет.** Бот видит Prometheus, Loki и сам
  алерт. События подов, условия нод и вывод `describe` в карточку не попадают - они
  попадают в `missing`, что честная версия того же самого.
* **Одна реплика и кэш последних инцидентов в памяти.** Журнал переживает
  пересоздание пода (`/data` - это PVC `triage-bot-journal`), кэш - нет; источник
  истины - журнал, и именно его читает `/incidents`. Когда `/data` был `emptyDir`,
  карточки переживали свои данные: кнопки вчерашнего сообщения отвечали «инцидент
  не найден», включая «📄 отчёт». Пересобранный кластер по замыслу начинает с
  пустого тома; на этом первом старте бот подтверждает пропущенные обновления
  Telegram, не отвечая на них, - нажатия, сделанные пока он лежал, не должны
  превращаться в пачку «инцидент не найден».
* **У вебхука нет аутентификации** - креденшел здесь NetworkPolicy, как и в стеке
  алертинга.
* **Таблица правил знает только алерты этого стенда.** Новый алерт - это новая
  строка плюс тест, и сначала падает тест; в этом и смысл.

M2 добавит исполнитель (отдельный компонент со своим ServiceAccount и одним узким
RBAC-правилом), блокировку действий по одобрению и проверку rollout после действия.
Whitelist, схема и каскад остаются ровно там, где они есть.
