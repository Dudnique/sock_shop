# Сетевые политики для namespace `sock-shop`

> [English](README.md) | **Русский**

Это файрвол для подов, а не упражнение в схемах: файлы здесь решают, кто с кем
может общаться внутри namespace. До переписывания каталог был идеальным
примером «безопасности, которой нет»: в нём лежал объект Namespace с
аннотацией `net.beta.kubernetes.io/network-policy` (способ до Kubernetes 1.7,
который современные кластеры просто игнорируют) плюс набор правил по сервисам
без `policyTypes` и **вообще без `egress`**. Стенд выглядел сегментированным в
`kubectl get -f`, а в реальности был открыт полностью: любой под мог достучаться
до любого пода, включая все базы и Redis, у которого в этом стенде нет пароля.

## Файлы

| Файл | Что защищает | Кому можно |
|---|---|---|
| `00-default-deny.yaml` | базовая линия namespace | никому — пока правило ниже не разрешит |
| `01-platform-traffic.yaml` | обязательный egress для всех подов | DNS (`kube-system:53/udp+tcp`), Jaeger (`jaeger:9411`) |
| `02-observability-and-probes.yaml` | метрики | Prometheus (`monitoring`) на 80/8079/9090 |
| `10-front-end.yaml` | `front-end` | вход: Traefik (`kube-system`), `loadtest` — выход: carts, catalogue, orders, user, session-db |
| `11-carts.yaml` | `carts` + `carts-db` | вход: front-end, orders — выход: carts-db:27017 |
| `12-catalogue.yaml` | `catalogue` + `catalogue-db` | вход: front-end — выход: catalogue-db:3306 |
| `13-orders.yaml` | `orders` + `orders-db` | вход: front-end — выход: orders-db:27017, payment, shipping, user |
| `14-user.yaml` | `user` + `user-db` | вход: front-end, orders — выход: user-db:27017 |
| `15-payment.yaml` | `payment` | вход: orders — выход: ничего |
| `16-shipping.yaml` | `shipping` | вход: orders — выход: rabbitmq:5672 |
| `17-queue-master.yaml` | `queue-master` | вход: ничего — выход: rabbitmq:5672 |
| `18-session-db.yaml` | `session-db` (Redis) | вход: front-end:6379 |
| `19-rabbitmq.yaml` | `rabbitmq` | вход: shipping, queue-master:5672 |

Объекты политик **аддитивны**: Kubernetes объединяет все правила, которые
выбирают под. Отсюда два следствия:

- новая политика никогда не делает namespace строже, она только открывает
  дырки, поэтому старый набор апстрима нельзя было «оставить на всякий случай»
  рядом с новым;
- `default-deny` работает потому, что запрещает всё, а остальные файлы
  возвращают обратно ровно конкретную дырку.

## Как применяется

`deploy.ps1` накатывает этот каталог отдельным шагом (после манифестов
приложения, перед мониторингом), поэтому обычный `.\deploy.ps1` даёт
сегментированный namespace. CI проверяет синтаксис каждого файла через
`kubeconform`.

## Как проверяется

```powershell
kubectl get netpol -n sock-shop          # 15 объектов вместо прежних 14
kubectl -n sock-shop get pods            # всё Running, пробы живы
# негативная проверка: под, которому здесь нечего делать, НЕ должен подключиться
kubectl -n default run probe --rm -it --image=busybox --restart=Never -- \
    timeout 3 sh -c 'nc -zv user-db.sock-shop 27017'   # ожидаемо: timeout
# позитивная проверка: приложение обязано работать целиком
start http://localhost:8080              # каталог, корзина, оформление заказа
```

Третья проверка — метрики: если политика забыла путь скрейпинга, в течение
минуты появляется `up == 0` по application-джобам, и срабатывает
`ScrapeTargetDown`.

## Грабли, найденные при переписывании

- **DNS — это egress.** При `policyTypes: [Egress]` без правила для DNS любое
  разрешение имени падает с «no such host», и это выглядит как баг приложения.
- **Пробы kubelet здесь НЕ блокируются** — и это измерение, а не догадка. В
  первой версии `02-observability-and-probes.yaml` была разрешена сеть узлов
  (`172.19.0.0/16`) «потому что пробы нельзя выразить через `podSelector`».
  Потом правило убрали и посмотрели на namespace: все поды остались `1/1
  Ready`, событий `Unhealthy` нет, `up == 0` по-прежнему 0. k3s использует
  kube-router, который не пропускает трафик от узла через политики, поэтому
  правило удалили, а не оставили «на всякий случай». На CNI, который всё-таки
  проверяет трафик kubelet (некоторые конфигурации Calico), его придётся
  вернуть — об этом написано в комментарии файла.
- **Неверный порт — это тихий отказ**: `catalogue-db` — MySQL (3306), а
  остальные три базы — Mongo (27017). Все порты ниже скопированы из описаний
  Service, а не по памяти.
- **`namespaceSelector` требует метку `kubernetes.io/metadata.name`** — её
  Kubernetes автоматически ставит каждому namespace с 1.21, и именно по ней
  матчатся `monitoring`, `kube-system`, `jaeger` и `loadtest`.
- **k3s отклоняет, а не дропает**: запрещённое соединение возвращает
  `ECONNREFUSED` за миллисекунды, а не таймаут. Для отладки это удобно, но
  полезно знать заранее, чтобы не решить «политика ничего не делает» только
  потому, что отказ пришёл быстро.
- **Пробник с метками рабочей нагрузки становится её частью.** Первая версия
  скрипта представлялась как `name=carts` — и HPA деплоймента `carts` посчитал
  его одним из своих подов и выдал `FailedGetResourceMetric ... missing request
  for cpu in container netpol-check-3`. Метки — это идентичность, и всё, что
  выбирает поды, использует их: значит probe-подам с чужими метками нужен
  `requests.cpu`, либо проверять надо через уже существующий под (именно так
  делает текущий скрипт).
