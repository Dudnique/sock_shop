# Локальный кластер k3d (Terraform)

> [English](README.md) | **Русский**

Декларативное описание локального кластера [k3d](https://k3d.io), на котором
запускается стек sock-shop. Один `terraform apply` создаёт кластер; `terraform
destroy` удаляет его.

## Зачем Terraform для локального кластера?

Кластер становится **воспроизводимой инфраструктурой как код** вместо
последовательности shell-команд, которые нужно помнить. Удали его, сделай
`apply` снова — получишь тот же кластер. Это тот же рабочий процесс, который
использовала бы реальная облачная инфраструктура; часть для AWS (удалённое состояние в S3 с
блокировкой в DynamoDB, EKS) запланирована, но ещё не написана (см. `TODO.md`).

## Требования

- [Terraform](https://developer.hashicorp.com/terraform/downloads) >= 1.5
- [Docker](https://www.docker.com/) (k3d запускает k3s в контейнерах Docker)
- CLI `k3d` удобен для инспекции, но провайдер общается с Docker напрямую,
  поэтому строго обязательным он не является.

## Использование

```bash
cd terraform/k3d

# Скачать провайдеры, объявленные в versions.tf
terraform init

# Посмотреть, что изменится
terraform plan

# Создать кластер
terraform apply

# Направить kubectl/helm на новый кластер (см. вывод `kubeconfig_path`)
export KUBECONFIG="$HOME/.kube/sock-shop-k3d.yaml"
kubectl get nodes

# Удалить всё
terraform destroy
```

## Публикуемые порты

Кластер публикует два вида хост-портов:

| Хост-порт | Порт контейнера | Кем обслуживается | Назначение |
|---|---|---|---|
| `ingress_http_port` (по умолчанию `8080`) | `80` | load balancer | Sock Shop через Traefik/Ingress |
| `ingress_https_port` (по умолчанию `8443`) | `443` | load balancer | HTTPS (зарезервирован под TLS) |
| `api_port` (по умолчанию `57443`) | `6443` | load balancer | `kubectl` - закреплён, см. ниже |
| каждый ключ `exposed_node_ports` | соответствующий NodePort | первая server-нода | тулы: Prometheus `9090`, Alertmanager `9093`, Jaeger UI `16686` |

Почему два механизма: приложение маршрутизируется ingress-контроллером (Traefik)
на единственном load balancer кластера, а тулы публикуются напрямую через свои
NodePort'ы. NodePort'ы обслуживаются нодами, а не балансировщиком, отсюда
node-фильтр `server:0`.

Grafana в этом списке **сознательно** больше нет. Раньше это был NodePort `31300`,
опубликованный как хост-порт `3000`, то есть «доступно на всех интерфейсах машины», и
отвечал он дефолтным `admin`/`admin`. Теперь её Service — `ClusterIP`, а сама Grafana
отдаётся через тот же вход Traefik, что и приложение, а различает их заголовок HTTP
`Host`: `deploy/kubernetes/manifests-monitoring/30-grafana-ingress.yaml`, хост
`grafana.localhost` (см. `FIXES.md`, раздел 12).

Чтобы опубликовать новый тул, добавь одну строку в `exposed_node_ports`
в `variables.tf` (или переопредели в `terraform.tfvars`) и сделай `apply` заново.
Больше ничего менять не нужно — с одной оговоркой, которая стоит времени, если её не
знать: провайдер k3d **не умеет менять существующий кластер**
(`Error: Updating clusters is not supported by k3d`), поэтому правка публикуемых портов
требует явного пересоздания:

```bash
terraform apply -replace=k3d_cluster.sock_shop
```

Обычный `terraform apply` на таком изменении падает, а так как тот же apply ещё и
пересоздаёт сгенерированный kubeconfig (destroy → create), после падения файла
kubeconfig на машине не остаётся. `deploy.ps1` теперь останавливается на ненулевом коде
возврата terraform, а не едет дальше.

## Пересборка стенда, который не возвращается

Кластер расходный: `deploy.ps1 -Down` удаляет его через `terraform destroy`, а следующий `deploy.ps1`
создаёт заново из этой конфигурации. Это первое, что стоит попробовать, когда ВМ Docker Desktop
пережила грязное выключение и `kubectl` уходит в таймаут: свежий кластер стартует при load ~0,5 на том
же лимите WSL в 7,5 ГБ, а старый (три дня снапшотов containerd, TSDB Prometheus и чанков Loki) — нет.

```powershell
.\deploy.ps1 -Down           # terraform destroy, ~20 с
.\deploy.ps1 -WithAIOps      # terraform apply + манифесты, ~5 мин
```

Kubeconfig, который пишет эта конфигурация (`~/.kube/sock-shop-k3d.yaml`, output `kubeconfig_path`),
перезаписывается при каждом apply, поэтому пересборка заодно чинит kubeconfig, указывающий на порт API,
которого больше нет. Теряется история — данные Prometheus, чанки Loki и журнал бота живут внутри нод, —
а не конфигурация: всё существенное в git.

Перед пересборкой `deploy\diagnose-stand.ps1` различает три отказа, которые выглядят одинаково как
«kubectl не подключается»: зависший движок, трэшинг ВМ, больной кластер. Скрипт read-only и печатает
следующую команду для того случая, который нашёл. Полный разбор инцидента и два бага `deploy.ps1`,
которые вскрыла пересборка, — в `FIXES.md`, раздел 17.

## Структура

| Файл | Назначение |
|---|---|
| `versions.tf` | Версии Terraform + провайдеров |
| `variables.tf` | Входные параметры (имя кластера, число нод, порты, ...) |
| `main.tf` | Ресурс кластера и файл kubeconfig |
| `outputs.tf` | Полезные значения, выводимые после apply |
| `terraform.tfvars.example` | Пример локальных переопределений |

> Сгенерированный kubeconfig пишется вне репозитория (по умолчанию
> `~/.kube/sock-shop-k3d.yaml`), потому что содержит учётные данные кластера.
